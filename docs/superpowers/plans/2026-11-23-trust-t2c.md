# witness trust T2c — Lint parts, readers and base-red — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run `ship.lint` as named parts that each run on their own, read four tools' diagnostics, and judge a part that is red on the base too per diagnostic — the plan's new diagnostics against the base's, which drive measures in the scratch when a gate asks — so a red base never blocks a plan that added nothing, and an opaque red base never reads green.

**Architecture:** `ship.lint` takes one command or `{name: command}` parts (schema 3, the battery precedent), resolved to `LintPart[]`; four `readers.<tool>` settings each read the part of the same name. Ship's lint lane runs every part (`runParts`, `src/lint-lane.ts`). A red part asks for the base's result by key; missing, the gate journals the key as `pending` on its `lint` check (`GateCheck.parts`), and the `base-lint` job kind — the first production kind (`src/base-lint.ts`) — owes exactly those keys: it runs the part, and its reader when red, on the base commit in the scratch, and returns the base's diagnostics as hashed keys. A reader's report is parsed per tool (`src/lint-readers.ts`); its paths are placed, and its error diagnostics keyed by (tool, rule, file, normalized snippet) (`src/diagnostics.ts`). The lane's per-part verdicts are the data T2d's registry and T2e's bookings read.

**Tech Stack:** TypeScript (ESM, Node ≥ 20), vitest, the git CLI; Biome's SARIF 2.1.0, ESLint's JSON formatter, cargo's `--message-format=json` lines, tsc's `--pretty false` lines.

**Spec:** `docs/superpowers/specs/2026-11-21-trust-design.md` — §3.2 (base-red), §3.7 (readers), §6 (Train A). The implementation map's T2c entry (`/Users/home/x/personal/witness/.superpowers/sdd/2026-11-21-trust/impl-map.md`, never committed) wins where it differs from the spec; this plan settles its two open questions and two departures (corrections C12, C13, the user's calls of 2026-11-23). 1. **Named parts.** `ship.lint` keeps its key (§4 T2) and takes one command — one part named `lint`, source `ship.lint` — or a map `{name: command}`, each part its own source `ship.lint.<name>` (the battery precedent: "a plain list is every class; a per-class map names all three"). Every existing file stays valid and every grant stands; no reshape step. A name is a lowercase letter, then up to 39 lowercase letters, digits or `-` (names ride job keys). Only the shape moves at schema 3; schemas 1–2 keep `text` through a per-setting `older` shape, so their pinned fingerprints hold. Every part runs, in file order, whatever an earlier one did — probe: fewhats' `biome check . && eslint . && pnpm check:ui` then `pnpm typecheck` stops at biome today (46 errors, all the old `.claude/hooks` payload, #95), so eslint, the UI scripts and tsc never run there. witness never parses `&&`. Parts take no turn (row 255). The lane stays one check named `lint`: the check's name is part of `checkOk`'s signature (`src/gate.ts:644`), so per-part names would append a round on every in-flight ship gate at upgrade.
2. **"build" is a named part** (the map's open question): a repo that wants its build to withhold review lists it in `ship.lint`. No setting, no check of its own.
3. **Readers are settings, one per tool, bound by name.** `readers.biome | eslint | clippy | tsc` (schema 3, default `none`, not ambient: an older file reads `none`, no reader), each a command whose stdout is only that tool's report, reading the part of the same name; any other part is opaque. `init` and `migrate` detect Biome (`readBiomeConfig`, `src/lint-config.ts`) and ESLint (a root `eslint.config.{js,mjs,cjs,ts,mts,cts}` or `.eslintrc.{js,cjs,json,yml,yaml}`) with the root lockfile's exec form — `pnpm exec`, `npx --no`, `yarn`, `bunx`; no lockfile, none: `<exec> biome check --reporter=sarif .` and `<exec> eslint -f json .`. tsc and clippy are never detected: their paths depend on where they run (probe: `pnpm -r exec tsc` prints each package's paths relative to that package, and stops at the first failing one). `check` warns `reader-unused` while a reader is set and no part bears its name, so after Train A's migrate both consumers are told how to split.
4. **Formats** (probe `t2c-readers.log`). Biome: SARIF — 2.4.9 carried all 46 results with no 20-cap, an absolute `uri`, no region for `format`, no snippet; the spec's "SARIF or checkstyle" → SARIF (JSON). ESLint: `-f json` — absolute `filePath`, `severity` 2 an error, a parse error `{ruleId: null, fatal: true}`, `source` on a file with messages; 109 KB for fewhats' green run, so a reader's stdout is captured whole (the runner keeps a 4,000-character tail). cargo: `--message-format=json` lines — **not probed** (no cargo on this Mac), built from cargo's documented message format; a human check on wot (Windows), as rows 201, 223 and 258. tsc: `<file>(<line>,<col>): error TS<n>: <text>` and the global `error TS<n>: <text>`, files relative to the cwd.
5. **A diagnostic** is (tool, rule, file, snippet) at error severity only — a warn-level rule is never a red (§4 T4). The rule is the tool's id (Biome `ruleId`, ESLint `ruleId` or `fatal`, cargo `code.code`, `TS<n>`); one outside `[A-Za-z0-9@/_.:-]{1,100}` reads `?`. The file is placed in the run's tree: a `file://` URI decoded, `\` read as `/`, an absolute path under the run folder (or under its real path: macOS tmp folders are `/var` → `/private/var`) made relative, a cargo span resolved against its manifest's folder. **A path witness cannot place stays as printed and is never dropped** (both trees print it alike; dropping it let a plan's new tsc error read green). Diagnostics on witness's own paths (`witnessPaths()`, current and retired) are dropped on both sides: they are never a plan's (fewhats' 46 Biome errors today). The snippet is the flagged line with whitespace runs collapsed and the ends trimmed (§3.7): the report's own copy where it carries one (cargo's span text, ESLint's `source`), else that line read from the placed file; `''` with no line (Biome's `format`) or no placed file. Keys are the first 16 hex of sha256 over the four fields.
6. **Compare on every file** (correction C12, the user's call): diagnostics compare as multisets over everything the reader reports, minus witness's own paths — not only PC files. A change can raise a diagnostic in a file it never touched: a type error in an importer, a rule it switches on. A rename makes the moved file's old diagnostics new (the file is in the key).
7. **Fails closed.** A reader run is readable when no signal ended it, its stdout parses whole as the tool's report, and it exited 0 or reported at least one error. Anything else — a crash, a config error, `pnpm run`'s banner before the JSON, `tsc --pretty` — refuses `reader-unread` in witness's own words: never parsed loosely, never green.
8. **The base's result on demand** (correction C13, the user's call; the map's open question "base-red in drive mode while the base job has not run yet"). A red part's key is `<part>@<base commit>.<h12>`, h12 the first 12 hex of sha256 over the part's and its reader's commands, so an edited command never reads a stale result. The lane reads it with `jobReading`; missing while a drive holds the repo, it is `pending` — red, as today's red lint — and the key rides the gate-run's `lint` check. The `base-lint` kind owes exactly the pending keys in each in-progress plan's last implement and last ship gate-run: drive lints the base only when a gate needs it, and a drive with no such key runs nothing new (no existing drive test journals one, so none changes). Per base commit, not per tree: the gate knows the commit, a job checks a commit out as itself (no pin), and two commits with one tree are rare.
9. **The base-lint kind.** `turn: false`, `gated: true`, `scratch: true`; `commands(cfg)` every part and bound reader; a 30-minute box (one reset, one prepare, a part and its reader; lint has no load rule, row 258's hand-off); one shard per key. The shard re-derives the key from its own fresh config (a key that no longer matches is refused), runs the part on the base commit in the scratch and, red with a bound reader, the reader there; it returns the base's keys with counts, at most 2,000 distinct keys (a result rides one pipe write of at most 48 KiB) — more is `unread`, never a truncated multiset. A step whose command a signal ended refuses `run-interrupted` (T2b's step contract).
10. **Per part, a verdict** (`PartVerdict.state`): `green` (exit 0) · `untrusted` (its command, or its reader when needed, not trusted) · `red` (the base is green: the plan's red) · `pending` · `not-measured` (the base's result is missing: drive will run it / nothing will — chat mode, two strikes, a malformed result) · `not-judged` (red on the base too, with no reader, or a report either side could not read) · `new` (red on the base too; the reader found diagnostics the base lacks) · `base-only` (red on the base too; nothing new). The lane passes on `green` and `base-only` only; every other state is red at ship, as a red lint is today. T2d assigns tiers; T2e books `not-judged` and `new` (human-only, §3.2).
11. **Drive reads the config as it stands at each job's start** (T2b slice 3 M7): gates read the file fresh, so a drive's run-start config made a mid-run edit to a part key a result no gate reads (pending for the rest of the run), and checked trust for commands the child no longer runs. The run's config stays for everything else (F9's precedent re-reads autonomy the same way).
