**Goal:** witness's own payload files stop counting as plan changes in every reader (#93), and a verify-red that dies mid-run never strands the plan's code: every verb that reads the plan's worktree puts the held work back first or refuses (#92's residual, correction C2).

**Architecture:**
- **#93 (row 246).** One primitive, the plan change set (PC): `planChangeSet(runRoot, base)` in a new `src/change-set.ts`. It is the diff against the base minus every harness's payload targets. Every reader of the diff calls it: the reviewed identity, the reviewer prompt (file list, diff text, coverage pool, snapshot, delta), evidence, verify-red and `next`. `changedFiles` stops being exported.
- **#92 (row 247).** The held-work machinery leaves `src/evidence.ts` for a new `src/held.ts`. One guard, `refuseHeld`, sits beside row 243's `refuseClash` in `test-evidence`, every code gate, `ship` (and before each of ship's commits) and `witness turn`. It puts the held work back under verify-red's own rules, or refuses `verify-red-pending`. `next` stays read-only and routes `witness recover`, which puts held work back. `start` names a held ref, `check` warns about one, and `contentSha` reads no sha while one stands. verify-red writes its held ref whenever it rewrites the tree, committed work included. A killed test run is never a red. A SIGTERM, SIGINT or SIGHUP during verify-red puts the work back before the process ends, where the OS lets a handler run.

## Decisions this plan settles (the map's open questions)

1. **Put back or refuse, per verb.** "This tree" is `--show-toplevel` of the tree the verb reads. A held ref is "here" when its record names this tree, or names no checkout or no files (fail closed).

   | Verb | A held ref here | A held ref recorded in another checkout |
   |---|---|---|
   | `verify-red` (its checkout) | puts back, then runs (0.30.0) | refuses `verify-red-pending`, naming that checkout (0.30.0) |
   | `test-evidence` (its checkout) | puts back, then runs | runs: this tree was never set aside |
   | `gate implement`, `gate ship` (the plan's worktree) | puts back, then judges | judges |
   | `ship`, at its top and before each commit | puts back, then goes on | goes on |
   | `witness turn` in a plan's worktree | puts back, then runs the command | runs the command |
   | `next` (and `--flow`, the dashboard, status) | routes `witness recover`; writes nothing | routes `witness recover` |
   | `recover` | puts each held ref back in the checkout its record names | — |
   | `start` | one `held:` line naming `witness recover` | the same |
   | `check` | warns `verify-red-held` | the same |
   | `contentSha` (decide, settle, screens) | `undefined`: the sha cannot be computed | computed |

   A put-back that cannot happen refuses `verify-red-pending` (exit 2). That covers a holder still alive, a held path touched since, a record with no files or no checkout, a gone checkout, or git unable to read the tree. The verb itself never runs then. `next`, `start` and `check` only read: `flowAction` is shared with the dashboard and status, so it must never write a worktree.
2. **Who puts back for `next`: `recover`.** `recover` is already the crash verb that `next` routes (the recovery fork), and the engine's row already runs `witness recover …` verbatim (`plugin/commands/witness.md`). The held row looks like the "worktree missing" row: no stage, no home, target the plan.
3. **The held record names its base** (`base: "<sha>"`, a new line). The put-back no longer needs a config, and a `--base` run goes back against the base it really used. A 0.30.0 record without the line falls back to the caller's `diffBase`.
4. **The held ref is written whenever verify-red rewrites the tree.** Today `holdWork` returns nothing when every non-test change is committed. Then the run still checks out base versions, and a crash leaves no ref for anything to read (found while planning). From now on a held commit equal to HEAD is written too, and every put-back goes through `restoreHeld`.
5. **Signals.** The runner uses `execSync` (`src/runner.ts`), so a handler cannot run during the suite. Probed 2026-11-21 (Node 24.11): with a SIGTERM listener installed, a group SIGTERM ends `execSync` first, and the listener runs only after a macrotask. Probed the same day: vitest catches SIGTERM and exits **143**, not by signal. So:
   - A run whose child ended by a signal, or exited 129, 130, 137 or 143 (128 + HUP, INT, KILL, TERM), is no outcome: `run-interrupted`, and nothing is journaled.
   - verify-red installs a trap for SIGTERM, SIGINT and SIGHUP from the moment it holds the work until it has put it back. The trap puts the work back and re-raises the signal.
   - `recordEvidence` yields one macrotask between the run and the journal write, so a signal that reached witness ends the process before anything is recorded.
   - SIGKILL, and Windows (whose tree stop runs no handler), leave the held ref for the guard. That is the "best effort" C2 names.
6. **What is witness-owned.** The union of every harness's payload targets (`HARNESSES` × `loadHarness(name).payload[].to`), whichever harness is installed. At 0.30.0 that is 9 paths. `.claude/settings.json` is shared, so it stays in PC. Probed 2026-11-21: `mergeSettings` returns `changed: false` on its own output, and `init` writes the settings file only at the primary root, never in a worktree. So `init --agent` into a worktree leaves the reviewed sha unchanged.
7. **The blind spot PC opens is closed in `check`.** Reviewers no longer see a session edit or delete a witness hook in its worktree. `check` already names an edited one (`payload-stale`, every home). A deleted one gets `payload-missing` (Task 3).
8. **Upgrade effect** (probed read-only on 2026-11-21). The reviewed identity drops payload paths, so a settled gate whose diff held payload files lapses once. In those consumers, an owed revise reads as answered and `next` routes a re-gate.
   - fewhats: `reply-send-plan-1` and `thread-mirror-tap-plan-1` each carry 9 payload files. Neither has a settled implement or ship gate: the first is parked at implement round 4, the second owes plan rework. Cost: none.
   - wot (`origin/main` 8328510): 4 plans are in progress and none is settled. `config-validation-plan-1` and `device-limit-plan-1` owe an implement revise (round 1). Their worktrees live on the Windows machine, so whether their diffs hold payload files is unprobed. If they do, each re-gates once on unchanged code unless edited first.
