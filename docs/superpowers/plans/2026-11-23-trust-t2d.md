# witness trust T2d — Check registry and the checks-only round — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A conflict marker or a red lint part ends a code gate's round before any lens runs — a checks-only round that spends no review budget, discharges nothing and offers no approve — the implement gate runs both checks too, the arbiter reads checks only as CLI facts, and a round red only because drive has not linted the base yet waits for drive instead of being revised.

**Architecture:** A registry (`src/checks.ts`) lists every machine check a code gate runs, with its tier (`withholding` or `judged`), in run order. The implement and ship gates hand it their checks as steps; `runChecks` runs the withholding tier first and cuts at the first withholding red. `judge` (`src/gate.ts`) journals a cut run as a gate-run marked `checks_only` — no battery, no verdicts — and one predicate, `lensesRan`, keeps such a round out of the budget, the verdict cache and the discharges, while `liveActs` drops approve on it. The arbiter's evidence renders checks from their structured fields only. A checks-only round whose lint red is only a base result drive still owes is `waiting` to the settle (`src/settle.ts`), which drive treats as work in flight; the result landing makes the round stale, so the policy routes the re-gate.

**Tech Stack:** TypeScript (ESM, Node ≥ 20), vitest, the git CLI.

**Spec:** `docs/superpowers/specs/2026-11-21-trust-design.md` — §3.2 (CR and the checks-only round), §3.9 (arbiter input), §4 T2. 3. **The checks-only round.** When `runChecks` cuts, `judge` journals a gate-run with `checks_only: true`, `model` = `pin`, `prompts_sha` = the full-review setup sha (the lenses, their docs, the pins and debts — what a battery would have been asked), `checks` up to and including the red one, `outcome: 'stopped'`, the snapshot fields any round carries, and nothing a battery writes: no `verdicts`, `malformed`, `skipped`, `rerolled`, `carried`, `standing`, `delta`, `setup_sha`, `junit`, stamps, repin or discharges. Its `round` is `roundsSinceApprove + 1`, so it shares its number with the round after it, as a malformed round does. Commit subject: `gate(<gate>): <target> round <n> checks only`. With the review withheld, `resolve` skips the prompt body (`promptBody: ''`): no lens reads it. `lastJudgedRun` keeps meaning "not malformed": a checks-only round is a run the gate's state anchors on — its decision is owed — but not one lenses ran.
4. **Resume.** With a withholding red, the gate resumes or answers changed-nothing only where its own pairing (`appendKind`) names a checks-only round with the same key and the same checks (`checksSignature`); every other case — fresh, cached, repair, a judged round, a checks-only round red differently — journals a new checks-only round. With no withholding red, a resume or changed-nothing whose entry is a checks-only round with other checks runs **fresh** (there are no verdicts to replay), so a fix or a trust grant on the same tree re-runs fresh (§3.2's acceptance). A malformed round followed by a checks-only round on the same key is not repaired but run fresh once the checks are green: rare, and only one battery more. `checksSignature` moves from `gate.ts`'s `checkOk` into the registry (T2c's hand-off) and gains each part's key, so a part command edited while a round stands moves the signature, and the round never resumes over a key no job owes.
