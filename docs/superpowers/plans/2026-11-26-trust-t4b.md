# witness trust T4b — Writers and tolerated sets — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When a fix's lint rule fires on old code, the old spots are tolerated and every new one is still caught — including the swap of one old spot for a new one that ESLint's own counts miss — and the lists that keep the tool green on main are witness's to write.

**Architecture:** Readers read *through* the tool's lists: ESLint's JSON report carries every bulk-suppressed spot (`suppressedMessages`, kind `file`) and Biome's SARIF carries every spot its witness-owned overrides set to `info` (level `note`), so one reader run gives errors and tolerated spots alike. A lint guard's proof reads the rule on the base too and opens a **tolerated set** — the ledger's fifth kind, one per (tool, rule), holding the old spots' keys. A new withholding check, `tolerated`, runs at implement and ship wherever a set applies: the plan's spots of each tolerated rule minus the **allowance** (its own sets whole, merged plans' sets capped by the lines the base still holds) is growth, red until fixed or booked by a human. Every code gate rewrites the two lists for its tree before anything reads it (`eslint-suppressions.json`, `biome.witness.json`); ship commits them after its rebase, which never conflicts on them; the lint effect writes each side's.

**Tech Stack:** TypeScript (ESM, Node ≥ 20), vitest, the git CLI.

**Spec:** `docs/superpowers/specs/2026-11-21-trust-design.md`. The sections it implements:
- §4 T4: "**Tolerated sets** (an LD item per (tool, rule)). Writers generate them on the base, compared as multisets: anything not in the base is new, whatever the counts. · New spots in a tolerated set are a T3 switch-off. · Tools with no writer (clippy, tsc, scripts) get no list, so the guard lands with zero old spots. · Ship's rebase regenerates witness-generated tolerated files." and the acceptance "A swap of one old spot for one new one is caught".
- §3.7: the writers' column — "ESLint | native suppressions at the root file, pruned" · "Biome | a witness-owned extended config with per-(file, rule) overrides, verified byte-equal" · "clippy | none" · "tsc | none".
- §3.3: the `tolerated-set` kind (subject (tool, rule), "multiset of old spots generated on the base"), "open | the CLI | guard proof".
- §3.2: "The AI judge never books markers, lint, evidence, criteria, regression or tolerated growth (row 172 holds)."
- §3.8 / §4 T1: the record's "tolerated spots left per (tool, rule)"; §8 "Tools without a writer (clippy, tsc, scripts) get no tolerated list."

1. **Size.** The map sized T4b M; it is L (11 tasks): the lint effect needs lists that match each side (point 10), every code gate rewrites the lists (point 9), and growth needs its own check (point 6). No split: each part is needed for a usable feature.
2. **What ESLint and Biome do with a list** (§1–§3).
   - ESLint 10.8.0: `eslint-suppressions.json` at the cwd, `{file: {rule: {count}}}`. Up to `count` violations of a rule in a file are suppressed (all of them), one more reports every one (Q4), fewer exits 2 ("suppressions left that do not occur anymore", Q5, Q7). **A swap inside a count passes** (Q3). `-f json` puts each suppressed spot in `suppressedMessages` with `suppressions: [{kind: "file"}]` (Q2); inline disables are kind `directive`. An exit 2 still prints one whole JSON report. ESLint writes the file with json-stable-stringify (keys sorted, two spaces, no final newline), and that file fails fewhats' `biome check` on the final newline alone (§2).
   - Biome 2.4.9 has no list (`--suppress` writes inline `biome-ignore` comments). A witness-owned file extended from `biome.json` works first or last in `extends`, and Biome concatenates its `overrides` with the repo's own (the repo's `noBarrelFile` overrides still hold). Overrides set to `"off"` hide every spot in a tolerated file, new ones too; `"info"` keeps the tool green — even under `--error-on-warnings` — and reports each spot as a SARIF `note`, a new one included; a reader with `--diagnostic-level=warn|error` drops them. GritQL plugin diagnostics all carry ruleId `plugin`, and no override removes them per file (B6).
3. **Readers read through the lists (correction C47).** ESLint's parser keeps each `suppressedMessages` entry of severity 2 with a `file`-kind suppression as a tolerated spot; Biome's keeps a `note` result where the run directory's `biome.witness.json` lists that (file, rule). `readPart` returns them beside its errors (`PartReading.tolerated`); every existing caller keeps reading errors alone (`diagnostics`), and only the guard, the `tolerated` check and the lint effect read both. The fail-closed rule counts errors only, and ESLint's exit 2 with a whole report is read (unused suppressions, Q5) — a stale list is what the gates rewrite, not an unreadable report.
4. **The tolerated set (§3.3).** A `ledger-open` of kind `tolerated-set`, check `tolerated`: `tool`, `rule`, `origin` (`guard` — opened by a lint guard's proof — or `book` — growth a human booked), `anchor` (the guard's), and `subject.spots`: each key (`diagnosticKey`: tool, rule, file, normalized line) with its file and copies, at most **500** keys (`MAX_TOLERATED_KEYS`, as `MAX_BOOK_KEYS`). Its key is 16 hex over (kind, check, plan, tool, rule, the sorted spots); the four other formulas do not move. A set applies to its own plan, and to every plan once its plan merged (C17's rule). It closes at the merge stamp when the merged tree holds none of its lines (line keys, as `booked-loosened`'s hidden spots), another plan's only where this merge took the last line out; at the abandon with its plan; by a re-proof that replaces it (`ledger-closed` gains `by: 'guard'`); or by `witness dismiss ledger`.
5. **The allowance is the ledger, not a base run (correction C50).** Per tolerated rule and key: the plan's own sets' copies, plus the merged sets' copies capped by the lines the plan's base holds (`lineKeys` over the base commit: a fixed line drops, two sets naming one key never allow more than the base's lines). No job, so chat mode reads it exactly. Its invariant: every spot of a tolerated rule on main passed a gate that read it as allowed or booked it.
6. **Growth is its own check (correction C46).** §4 T4 says new spots are "a T3 switch-off", but §3.2 bars the AI judge from booking tolerated growth while `switch-offs`' waiver is the judge's — and the arbiter's menu filters bookings by the check's waiver (`menuFor`). Growth is a lint diagnostic a list hides from its tool: a new check, **`tolerated`**, **withholding**, **the human's waiver**, right after `markers` and before `lint` (so a missing Biome `extends` names its own remedy before Biome's errors withhold at lint). It runs only where a set applies, so no other plan's round gains a term. Red: growth in any rule, or a rule not measured (reader unset, untrusted or unread; Biome not wired; a Biome reader hiding notes; a list the repo gitignores). The policy revises (rule `checks-only`); a human may `--book tolerated`, which opens a `book` set per rule for its growth.
7. **Biome overrides set `info` (correction C48),** never `"off"`: the tool stays green and witness reads every tolerated spot in the same run. One override per file, each tolerated rule of the file set to `info`, in `formatJson`'s style (Biome collapses `"includes": ["x"]`; probe B7). `biome.json` must list `./biome.witness.json` in `extends`; witness never rewrites `biome.json` (it may be JSONC with comments) — the guard says the edit and the check reads `biome-unwired` until it is made.
8. **Writers are witness code (correction C49).** No writer command, no setting, no trust grant, schema 4 untouched. The ESLint list is ESLint's own layout (`formatJson` over keys sorted at every level) plus the final newline Biome wants. A plugin rule (`plugin`), clippy and tsc have no list: the guard lands with zero old spots, as in T4a.
9. **Every code gate rewrites the lists (correction C51).** In `resolve`, after the base is known and before the change set is read: the tolerated tools' readers run in the worktree (`ensureTrusted`, as lint's), and each list is written for the tree — ESLint: every spot of a tolerated rule counted per (file, rule), growth included, so the tool never reports one and the check alone judges; a rule a set once named but none applies to now gets no entry; the repo's own entries (rules no set ever named) kept at most at the base's count. Biome: the witness file, never deleted once present — byte-equal to what witness generates by construction, since every gate writes it (§3.7's "verified byte-equal"). The rewrite runs wherever a set applies or a list still holds what witness wrote (an ESLint entry of a rule a set once named, or any Biome override), so a closed or dismissed set's entries go. Implement leaves them uncommitted (the reviewed identity reads the worktree); ship commits them with the trailer, as `dropRetired`. **Ship's rebase passes a merge driver for the two files** (`-c core.attributesFile=<temp> -c merge.witness-tolerated.driver=true`, probe §6): the rebase keeps the upstream's lists and never stops on them, and the gate rewrites them after.
10. **The lint effect writes each side's lists (correction C51).** A lint guard's plan changes `eslint.config.*`, so the effect runs; its effect side holds the base's config with the plan's list, ESLint exits 2 on the unused entries, and `loosenedOffs` names a loosened part — a false switch-off on every lint-guard plan with an ESLint list (§4, by reading). Each side, before its parts run, reads its tolerated tools and writes lists for its own code (every open set's rules, repo-wide; the repo's own entries kept at that side's counts), and `hidden` compares errors and tolerated spots on both sides.
11. **The guard reads the base (correction C52).** A lint proof runs the reader on a third tree, `old` = the base commit with the overlay folded over it (through the base's scripts). Red counts the rule's spots in the anchored file beyond the old tree's spots there, and green requires none beyond them — T4a's red counted any spot in the anchored file, so a rule firing only on a line the base already held proved red without catching the flagged code. The old tree's spots of the rule, minus what merged sets already allow, open the plan's set in the guard's own transaction, replacing the plan's earlier `guard` set for that rule. More than 500 keys opens none (T4a's behavior).
12. **The record's tolerated spots (§4 T1).** Per (tool, rule) of the open sets whose plan merged, the copies main's HEAD still holds (the allowance's cap over HEAD); measured once the checks fold is.
13. **Upgrade.** No set exists until a lint guard with old spots is proven after Train B, so no in-flight round gains a term and nothing re-reviews; fewhats and wot hold no list. The lint effect's change reaches only plans with a set.

3. **The repo's own ESLint entries** (pre-witness suppressions in the base's list). They are kept, never raised above the base's count, and never read as growth; a plan that raises one finds it written back and ESLint reporting the new spot. → Task 4 and Task 6, "the repo's own ESLint entries stay at the base's count".
4. **Biome left unable to report tolerated spots** — `biome.json` not extending the witness file, or `readers.biome` holding `--diagnostic-level=warn|error`. The check reads not measured (`biome-unwired`, `reader-hides-notes`), never green. → Task 5.
5. **The arbiter at a growth stop.** The menu holds no `--book tolerated`; the policy revises; only a human at a terminal books. → Task 7, "the arbiter and the policy never book tolerated growth".
