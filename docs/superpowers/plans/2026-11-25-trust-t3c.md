# witness trust T3c — What a plan's check-definition changes hide, and booking it — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A plan that changes a file the base uses to define its checks — `.gitignore`, a lint or type config, a `package.json` script, a test-runner config — so that its tree passes where the base's definitions would fail it is a judged red in the `switch-offs` check at implement and ship. The red is booked by the AI judge or the human like a switch-off line, and the booking closes once main no longer holds what was hidden.

**Architecture:** A new setting, `checks.definitions` (schema 4), lists the definition files. When a plan modifies or deletes one the base holds, the gate builds an effect tree: the plan's tree with the base's copies of those files folded back in (a `package.json` keeps its own bytes except the listed member, spliced). Both trees are pinned as wrapper commits, and a new drive job, `lint-effect`, runs every lint part and every set reader on each in the scratch. A diagnostic a reader reports under the base's definitions beyond what it reports under the plan's is a hidden diagnostic. A part that passes only under the plan's definitions, where its own reader names nothing, is a loosened part. A new withholding check, `definitions`, is red only while drive measures the effect (T2d's checks-only wait), and the `switch-offs` check folds the hits beside its lines and lost specs. The ledger gains a fourth kind, `booked-loosened`, closed at the merge stamp.

**Tech Stack:** TypeScript (ESM, Node ≥ 20), vitest, the git CLI.

**Spec:** `docs/superpowers/specs/2026-11-21-trust-design.md`. The sections it implements:

1. **Hidden diagnostics and loosened parts (correction C34).** The spec counts a diagnostic "on a PC line" that the plan's own definitions do not report. As built, there are two instruments.
   - **Hidden diagnostics.** Every set reader (`readers.<tool>`, bound to a part or not) runs on both trees. A diagnostic the reader reports on the effect tree beyond its count on the plan's tree is hidden. The comparison is a per-key multiset, as base-red's is (row 263). It covers every file the tree tracks, minus the definition files the effect restored, and only diagnostics that carry a file. This follows C12's rule (the user's call): a definition change can hide a diagnostic in a file the plan never touched.
   - **Loosened parts.** Every `ship.lint` part runs on both trees. A part that exits 0 on the plan's tree and non-zero on the effect tree is loosened, unless its own bound reader named a hidden diagnostic (that reader's diagnostics already say what the part hides).
   - **Why both** (`t3c-effect.log` §1, §4):
     - In fewhats, a tracked file listed in `.gitignore` vanishes from both Biome (`vcs.useIgnoreFile`) and ESLint (`includeIgnoreFile`): 1 + 1 errors become 0 + 0, and both parts go green. A reader sees this.
     - A neutered script (`"lint": "true"`), or a file added to the inline allowlist in fewhats' `scripts/check-ui-tokens.sh`, moves no reader. Readers run their own commands, so only the part's exit sees it.
     - fewhats' `ship.lint` is one opaque part, `pnpm lint && pnpm typecheck`, and no tsc reader is set. A `tsconfig` loosening there is seen only through the part.
2. **What the effect tree restores (correction C35).** Restoring "the base's definitions" literally would undo a plan's legitimate definition work.
   - **Modified or deleted** definition files go back to the base's copy. A deleted one is restored only if the plan's tree still tracks a file in its folder. A plan that removes a package wholesale (its sources and its `tsconfig.json`) hides nothing.
   - **Added** definition files stay as the plan wrote them. 33 of the 83 definition touches in fewhats' 22 merges were added files (each new package's `package.json` and `tsconfig.json`), and removing them would break every new-package plan. The one exception is an added ignore file (basename `.<letters>ignore`, such as a nested `.gitignore`): it can only hide, so the effect tree removes it.
   - **`<glob>#<member>`** entries restore one top-level member of a JSON object: the base's member value text is spliced into the plan's file, and every other byte stays the plan's. Such an entry applies only when both sides parse as JSON objects, both hold the member, and the values differ. A member on one side only is not a loosening: a missing `lint` script fails the plan's own part.
   - **Why the member rule:** 37 of the 39 fewhats `package.json` edits touched only `dependencies`, `exports` or `devDependencies` (the map's "48 of the 50" counted every modified definition file). A whole-file revert would break `--frozen-lockfile` and undo dependency work (`t3b-defs.log`). The splice kept `biome format` clean on both real pairs (`t3c-effect.log` §2).
   - TOML sections (`Cargo.toml [lints]`) wait for a Rust consumer to probe (Open). Symlinks and submodules at a definition path are never restored.
   - **Replayed** with real tools on two fewhats merges (§3): restored `scripts`, and a restored `.gitignore` plus a removed nested one. Both read no hit. Part exits and reader diagnostics were equal, and each side took under 20 s.
3. **`checks.definitions` (schema 4, Train B's step; T3a and T3b left it open).**
   - Shape `definitions`: a list of entries. Each is a repo path or glob of 1–200 characters from `[A-Za-z0-9._*@+/-]`, optionally followed by `#<member>` (`[A-Za-z0-9_.@-]{1,100}`). It never starts with `/` and has no empty, `.` or `..` segment.
   - An entry without `/` matches the basename at any depth; one with `/` matches from the root. `*` matches within a segment and `**` across segments (`globToRegExp`, `src/glob.ts`). The first matching entry wins.
   - Not ambient: an older file reads the default list in memory, as `checks.switchOffs` reads `[]`. `migrate` writes it (`added:`), and `check` names the feature off when the list is `[]`.
   - **The default, verbatim:** `['.gitignore', '.eslintignore', '.prettierignore', '.editorconfig', 'biome.json', 'biome.jsonc', 'eslint.config.*', '.eslintrc*', 'prettier.config.*', '.prettierrc*', 'tsconfig*.json', 'jsconfig*.json', 'package.json#scripts', 'vitest.config.*', 'vitest.workspace.*', 'jest.config.*', 'playwright.config.*', 'stryker.config.*', 'stryker.conf.*', 'clippy.toml', '.clippy.toml', 'rustfmt.toml', '.rustfmt.toml', 'ruff.toml', '.ruff.toml', '.golangci.*']`.
   - Setup files such as `vitest.setup.ts` are code, not definitions (the map's leaning): reverting one would read the plan's own tests' imports as hidden.
4. **The job and its wait (correction C36).**
   - **`lint-effect`** is gated (a gate waits on it), takes no turn (lint takes none, row 255), runs in the scratch, and is boxed at 1,800,000 ms.
   - **Its key** is `<plan commit>.<effect commit>.<h12>`. Both commits are wrapper commits the gate pins with `pinTree` (`refs/witness/cf/<plan>/<tree>`, dropped at the merge stamp). `h12` is 12 hex over the sorted part `[name, cmd]` pairs and the sorted set reader `[tool, cmd]` pairs, so an edited command never serves a stale result.
   - **Why commits:** a plan id has no length cap, and a job key caps at 200 characters (`isJobKey`). A key built from commits is 94 characters, or 142 for sha-256.
   - **One shard** runs both trees under one scratch hold (`withScratchLock` is re-entrant). It returns each part's exit on each side, each reader's unread reason, and the hidden diagnostics. These are `{ tool, rule, file, line?, key, count }`, sorted by file, line, tool and rule, and kept while the result's JSON stays within 40,000 bytes (the verb's 48 KiB pipe cap, row 257). `over` counts the rest. No snippet ever rides the result.
   - **The `definitions` check** is withholding, right after `lint`, with no waiver. It is red only while the result is pending under a drive, and then it owes the key. With no drive, with scratch runs off, or after two strikes, it reads not checked: green, said in its detail and its `lint_effect`, and the key is still owed so that a drive started later measures it (C13's rule, as base-lint has it).
   - **T2d's wait** (`baseWait`, row 267) reads a checks-only round whose last check is `definitions`. It is `waiting` while drive will run the key, and `landed` otherwise: a result arrived, the config no longer gives the key, scratch runs went off, or the job was struck. The re-gate then reads the effect. It is never `red`. The withholding check's owed key joins the resume signature, so a round never resumes over a key no job owes.
   - **Gates add the step only when the plan changes a definition the base holds.** Every other plan's round carries no `definitions` term, so its resume signature does not move on upgrade.
5. **The hits in `switch-offs`.**
   - A third `OffVerdict` variant, `kind: 'loosened'`, is a hidden diagnostic (`tool`, `rule`, `file`, `line?`) or a loosened part (`part`, `defs`).
   - **A hidden diagnostic's key** is 16 hex over `['loosened', tool, rule, file, snippet]`, computed in the job (`loosenedKey`, `src/diagnostics.ts`).
   - **A part's key** is 16 hex over `['loosened-part', name, cmd, the sorted defs]`. `defs` maps each restored path (a member as `package.json#scripts`) to the base side's identity: its blob sha, `json:` plus 16 hex over the base member value's JSON, or `null` for a removed added ignore file. A further definition edit therefore mints a fresh hit.
   - The hits are journaled after the token lines and lost specs, and `MAX_OFFS` counts all three. An effect with `over` journals no loosened hit and reads red: nothing is bookable.
   - The detail appends the loosened segment, the reviewers' note gains a row per hit and one row naming the definitions changed, and `checksSignature` reads each hit by key and unbooked count, as it already does for every hit.
6. **The booking (correction C37).**
   - **The fourth kind, `booked-loosened`.** Hidden diagnostics are booked one item per `(tool, rule)`, with `subject.hidden` mapping each key to `{ file, copies, lineless? }`. A deliberate rule relaxation is then one dismissal (`rule-retired`), not one per spot. A loosened part is booked one item per part, with `subject.defs` the hit's `defs`.
   - The key is 16 hex over `(kind, check, plan, tool ?? null, rule ?? null, part ?? null, the sorted subject)`. The other three formulas do not move.
   - **The judge or the human books it** through T3a's `--book switch-offs`, with the same liveness, the same terminal rules and the same `waivable` hand-off. The check applies the plan's own open items only (C17).
   - **It closes when main no longer holds what was hidden**, at the merge stamp of plan M, read from M's newest ship round, in T3a's shape:
     - A hidden item closes when no key it books is held by its file in that round's `reviewed_tree`: no line of the file has the item's tool, rule and file with that normalized line. A lineless key (a whole-file diagnostic, such as Biome's `format`) closes only once its file is gone.
     - A part item closes when that tree holds every base-side identity in its `defs` again: the loosening was reverted.
     - M's own items read the tree alone. Another merged plan's items close only where the round's `reviewed_base` still held them and the tree does not: this merge did it. Nothing reads gone by absence.
7. **Inline disables stay the token layer's (correction C38).** The spec's effect layer claims inline disables too. The base's definitions carry no inline directive, and a reader cannot be told to ignore them without witness appending a flag it does not own. Inline directives remain T3a's token layer. A directive split across lines stays a residual, and DESIGN.md's Open entry that names "T3c's lint effect is the catch for lint" is amended.
8. **The judge's facts and the block's words.**
   - The arbiter reads `<tool>: <n> diagnostic(s) the plan's check definitions hide (<k> rule(s))` per tool, `part <name> passes only under the plan's check definitions` per part, and `lint effect not checked`. It never sees a path, a line number, a rule id, a part command or the not-checked reason. Part names are the repo's own config, spelled out.
   - Rule `waivable` names the loosened hits beside the lines and lost specs, and offers restoring the check definitions. The booking's tradeoff and the arbiter's prompt widen to hidden rules and loosened parts.
9. **The test suite's fixtures.** The seeded base holds a `.gitignore` (witness's local entries), and the `vitest-single` fixture's own `.gitignore` (`node_modules/`) overwrites it. Every `shippableRepo` plan therefore reads `M .gitignore` (`t3c-effect.log` §5) and would owe an effect job, and a drive-held test would wait on it. Both fixture `.gitignore` files are deleted (the repo's root `.gitignore` already ignores `node_modules/` at any depth), and a test pins that a fixture plan changes no definition its base holds.
10. **Left out, recorded (Open, in Task 10).**
    - An added definition file other than an ignore file, such as a nested `biome.json` or `tsconfig.json`, can loosen its subtree unseen.
    - TOML sections wait for a Rust or Python consumer.
    - A tool upgraded together with its config reads the base's config through the new tool. A part that crashes there is a loosened part the judge must book.
    - The plan's side runs in the scratch, so a difference only the worktree's environment shows is not seen.
    - A loosened part's item closes only when the base's definitions return, or by dismissal.
    - An ignore-file edit that hides nothing tracked still costs one job (there is no pre-check).
    - Chat mode reads not checked.
    - T3b's and T3a's deferred minors stay deferred, and the ledger ↔ switch-offs import cycle (T3a unit M-f) is not widened: the close helpers live in `src/diagnostics.ts` and `src/definitions.ts`.

## Review Focus

The input classes T3c's tests must not leave to chance, most likely first:

1. **A plan that adds a package** (a new `tsconfig.json` and `package.json`). There is no `definitions` check and no job: an added definition stays as the plan wrote it. → Task 2, "an added tsconfig.json stays as the plan wrote it"; Task 4, "a plan that changes no definition the base holds runs no definitions check".
2. **A `package.json` edit that touches only dependencies.** It is not restored, and nothing is owed. → Task 2, "a package.json whose scripts did not change is not restored".
3. **A plan that removes a package wholesale.** Its deleted `tsconfig.json` is not restored, so the type check does not crash on an empty folder and no loosened part is invented. → Task 2, "a deleted tsconfig.json whose folder the plan emptied is not restored".
4. **A part that writes files the tree does not track** (build output) that the base's `.gitignore` would not ignore. Those diagnostics are never hits. → Task 3, "a file a part writes that the tree does not track is never a hit".
5. **A reader that cannot read its report under the base's definitions** (a tool upgraded together with its config). It gives no hit and names why, while the part's crash still stands as a loosened part for the judge. → Task 3, "a reader unread on the effect tree gives no hit and says why"; Task 6, "the definitions check names an unread reader".
