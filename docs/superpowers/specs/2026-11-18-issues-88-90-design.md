## 2. Goals, non-goals, anti-goals

**Goals**
- g1. One stop, one decision: no settler's act lands on a disposition it did not read, and a settle that loses is a no-op, never a park (#88).
- g2. One model call per stop, and one ship run per plan, wherever drive, a chat and a terminal meet; a miss costs a call or a run, never a wrong record.
- g3. The chat is woken only for what needs the human, and once.
- g4. A plan's unbuilt steps are its next work before and after an implement gate, and no gate runs while one is open (#89).
- g5. Every parked gate offers a way back that can succeed (#89).
- g6. A hold only the human can clear is a human stop: reported once, no more sessions, not stuck, no `witness retry`, a wake that names it — and it survives a drive restart (#90).
- g7. A hold that clears by itself is re-checked by drive, within its caps.

**Non-goals**
- n1. Who settles is unchanged — the policy, the arbiter, the kept stops (row 173); only what happens when two try at once changes.
- n2. No full lease: no renewal thread, nonce fence, cross-target claim or session handle (the user's pass-4 answer).
- n3. No new committed setting and no `witness migrate`: every new bound is a constant or derived from an existing setting (row 202's precedent).
- n4. A lock miss — a holder frozen past its bound, a reused Windows pid — may still let a second settler pay one more model call; the record stays right.
- n5. Witness never withdraws a ship approval because CI failed; a red CI is the human's.

**Anti-goals**
- A park, or any settler's act, appended on top of a decision it never read.
- Telling the human to retry what cannot change, or offering a merge for a PR whose branch, target or CI is not what an approval can merge.
- Waking the chat for a stop drive is deciding.
- A plan step left unbuilt behind a passing implement gate.

**Constraints**
- c1. Witness only; upgrading a consumer is the user's call, made separately.
- c2. An upgrade must not re-queue a plan or leave a tree dirty. New files live under `.witness/live/`, which state commits already exempt (`src/gitio.ts:126`) and the live writer excludes first (`src/live.ts:50`).
- c3. Windows behavior is measured by the human before a row says MEASURED (W1–W7, §7).
- c4. 0.29.0: a new journal entry kind and a newly legal decision. Once a 0.29.0 CLI journals anything, the state floor — the highest `w` stamp in the journal (`src/floor.ts`, row 116) — refuses every older CLI at dispatch. An older drive already running is not refused, because the floor is read only at dispatch (`src/cli.ts:187-199`; P13).

## 4. The design

### 4.1 Row 240 — one decider per stop (#88)

A token checked under the state lock keeps the journal right (§4.1.1). Busy locks (§4.1.2) only spare model calls, duplicate ship runs and false wakes, so a lock that misses costs a call or a run, never a wrong record. *(The split is the user's pass-4 decision; the mechanism is my call.)*

#### 4.1.1 The settled-since token (R2) *(my call, from passes 2–4)*

- Every settler's act — the policy's, the arbiter's, `parkRefused`, the park after two malformed answers, a cap park — carries a token: a hash of every `human-decision` line of that gate after the run it judged (that gate's `caused_by` reopens included), taken from the settler's own read before any model call: `settleStop`'s read, or `parkAtCap`'s.
- `applyDecision` compares the token first, before the repair, bound and anchor checks, and again under the state lock beside the `nothing-pending` and `anchor-moved` re-read (`decide.ts:614-625`). A mismatch refuses `settled-since`.
- `settleStop` turns `settled-since` into a new `Settled` kind naming the winner, printed `decided: <gate> <target> → <decision> · <by> (decided first)`; the skills key on `→ revise`. After any refusal it reads the stream again, and a different `run_id` or token is a no-op.
- `parkRefused` runs only for an arbiter choice refused on a run still owed in the same form — the same `run_id` and the same token — and carries the original token. A stale-verdict or hold-lifted refusal never parks: the content moved, and it is judged again.
- Human acts carry no token. A human's `decide` while a settler's arbiter thinks wins, and the settler's act refuses `settled-since`.
- Applied with no lock at all, the token refuses the loser in all 8 race shapes, the journal keeps the winner, and the 102 tests of seven decision test files pass unchanged (P4).

#### 4.1.2 Lean busy locks (R1) *(the user's decision; the shape is my call)*

- **Where.** `.witness/live/busy/<target>.settle.json` and `.witness/live/busy/<plan>.ship.json` — machine-local, under the folder state commits exempt (c2), refused through a symlinked folder as `live.ts` refuses one. A target names a file only after it passes the id rule.
- **Shape.** Created exclusively and without following a link (`O_CREAT | O_EXCL | O_NOFOLLOW`), holding `{pid, since, until}`. `until` is its taker's own bound for the longest legitimate hold, so no reader computes one from its own config. An empty or unreadable file is a write in progress for one second, as the repo lock reads one (`src/lock.ts:12-14`).
- **Live** means the pid is alive and `until` has not passed; a lock whose `until` lies more than 24 hours after its `since` reads as stale. A lock that is not live is taken over through `takeStale`'s steal guard, as the repo and drive locks are (`lock.ts:76-95`). `EPERM`, `EBUSY` or `EACCES` on create or unlink (a scanner on Windows) reads as busy after a few retries within a second, and the caller does nothing this time. Nobody ever waits for a lock.
- **The settle lock** is taken by `settleStop` before it reads the stop — the gate tail's settle, ship's awaiting-decision settle, `next`'s pass and drive's pass all go through it — and by `parkAtCap` before it reads the stream; it is held through the arbiter call and `applyDecision`, and released in `finally`. Its `until` is `since + 2 × 3 × gates.reviewerTimeoutMs + LOCK_WAIT_MS + 60 s`: a self-repair reroll is a second arbitration, each of up to three timed attempts (`src/reviewer.ts:146`), then the door's lock wait. Held by another live process: `settleStop` returns `Settled` `busy` and reads nothing; `parkAtCap` reports busy and parks nothing.
- **The ship marker** is taken by `witness ship` at its start, before it journals anything, and released in `finally`. Its `until` covers the gate's battery, the CI watch, both settles and the git and gh calls: `since + 3 × gates.reviewerTimeoutMs + ship.ciSettleMs + 30 min + 2 × the settle bound + 10 min`. Held by another live process: `witness ship` refuses exit 3 before journaling, `busy: <plan> — witness ship is running on it (pid N, since HH:MM) · nothing to do; it continues when that ends`. It is a separate file from the settle lock, so ship's own gate tail never nests on it.
- **Drive.** `admits()` skips a target whose settle lock or ship marker another live process holds, so the settle pass, the fill, `waitingNeed`, `capped` and `unmoved` never meet it. While an admissible target is busy, or a settle was left with exit 3, and no lane runs, drive polls on its pause cadence — no pause for the human, no notification — instead of ending its run. The busy folder joins `watchSignature`; a lock is never renewed, so only a take or a release changes it. Drive drops the locks of dead pids when it starts and after every session, `releaseDeadTurn`'s pattern (row 218), before Windows can hand the pid to another process. *(v4 gave each lock a `session` field for that cleanup; a dead pid is the whole test, so it is dropped — my call.)*
- **A lane whose target is busy when it ends** — a human started `witness ship` after drive spawned — ends like a usage-limited lane: progress cleared, no cap counted, never stuck. Drive reads the busy folder for it, not the session's words *(my call: v4 heard the `busy:` line; the folder is the record)*.
- **An older drive.** `drive.lock` gains `busy: 1`, on row 224's `lease: 1` precedent. A 0.29.0 `next` or `wait` that sees a live drive lock without it settles nothing and prints `wait: older drive — a witness drive from before 0.29 runs this repo · stop it, then say go` with that drive's stop command on a `run:` row (the `watch:` line's stop, rows 180 and 201). A 0.29.0 drive reads the state floor each round and, once a newer CLI has written, ends with `EndReason` `superseded`, "a newer witness CLI took over". The release notes say to stop drive before upgrading.
- **What a miss costs.** A holder frozen past its `until` (a sleeping host) or a reused Windows pid lets a second settler or ship run in: one more model call, or one duplicate ship run, never a wrong record (the token, and a merge pinned to its head). A dead pid frees at once; a reused one at `until`.

#### 4.1.3 Cap parks (R3) *(my call, from pass 3)*

A cap park lands where it does today, on the latest open gate (`caps.ts:71-72`), now under the settle lock and with a token from `parkAtCap`'s own read. One after a `revise` or `revise-upstream` is drive's deliberate flow park (row 183), and its parked row offers the revise alone (§4.2.5), which lifts it with the upstream reopen intact (P5). Retargeting the park onto the reopened gate was probed and dropped: the park discharged the reopen, and the revise then lost it. The invariant is "no settler's act lands on a disposition it did not read": #88's third Expected holds for every settler, while a cap park or a human's D94 stop after a revise stays legal (fewhats has five such runs, all done or abandoned).

#### 4.1.4 Retries (R4) *(my call)*

A settle left with exit 3 — a busy lock, a pending transaction, which `settle.ts:82-83` already calls transient — and a lane whose target is busy when it ends are tried again at the next round: never set aside, stuck or "needs you". Today drive sets aside every `left` (`drive.ts:896-898`).

#### 4.1.5 What wakes and routes the human (R5) *(the user's decision "the chat leaves drive's stops to drive"; the readers are my call)*

- **Drive's scope.** The live file (`.witness/live/drive.json`) gains drive's scope: the claimed flow under `--flow`, else every target. A stop **drive will decide** is one in its scope that drive has not set aside. Every lane is in the scope, so v4's "lanes" add nothing *(my call)*.
- **The chat's `next` under a live 0.29.0 drive** settles only stops drive will not decide: outside its scope, or set aside by it (a stop left for a human after an arbiter failure stays the chat's to retry, as today). Its printed route skips a stop drive will decide, or one under another process's live settle lock, naming it once — `note: being decided — <gate> <target>` — and `next: witness decide …` prints only for a stop that needs the human. With no live drive the chat settles repo-wide, as today.
- **`needsYou`** — and through it `wait`, the report and drive's notifier — lists an owed decision in drive's scope only once drive set it aside as left for a human, never for an exit-3 settle or a usage-limit pause, and a pending transaction under a live drive only once drive set the recovery aside. Drive applies the same rule to itself.
- **A stop under a live settle lock** is being decided, whoever holds the lock. `wait` keeps it in its list but never shows it, never counts it new and never prunes it; `seen` gains an item only when the item is shown, so a stop that frees still owed wakes the chat once, and one decided meanwhile leaves silently. The token counts every key, busy or not, and `wait --since` takes a token equal to the list with its busy items or without them as no news, so a stop turning busy, or arriving busy, wakes nobody.
- These filters touch only what the human is shown — `humanAction`, `needsYou`, the printed route — never the ladder drive keys progress on.

#### 4.1.6 The gate's reopen re-read (R6), and old journals *(my call, from pass 3)*

- A pre-existing lost instruction (P6): a `revise-upstream` that books a reopen of a gate while that gate's battery runs is discharged by the run that lands after it. The gate's under-lock re-read (`src/gate.ts:583`) now refuses to append its run, exit 3, when a reopen of this gate landed after the gate read its stream (`gate.ts:361`); `next` routes the gate again and the next run sees the reopen. One battery is thrown away. A human's `decide --revise --upstream` takes no lock on the upstream target.
- Parks the old race wrote stay in old journals; the un-park (§4.2.5) lifts them.

### 4.2 Row 241 — unbuilt steps come first (#89)

#### 4.2.1 Routing (R7) *(the user's decision; the placement is my call, from pass 2)*

An open plan reopen and an open step route above `flowStep`'s `pr` row (`next.ts:441`), and an open step is the next work before or after an implement gate: the `stepped` term drops `!implementGated` (`next.ts:475`). This amends row 95, whose reopen row moves above `pr`, and reverses row 191's Plan's call 5.

#### 4.2.2 `--step` (R8) *(the user's decision; the wording corrected in pass 2)*

`test-evidence` and `verify-red` require `--step` before the first implement gate, as today, and after it while any criteria step is open (`src/steps.ts:180-183`). A fix round, with every step closed, names none.

#### 4.2.3 The steps-open refusal (R9) *(the user's decision Q6; ship's part is my call, from pass 2)*

`gate implement`, and a human's `witness ship`, refuse `steps-open` while a step is open — before the battery, journaling nothing, naming the step's command — and `decide`'s refusals name it too. The ship gate's `implement-gate` check (`src/gates/ship.ts:77`) fails while a step is open, and ship's merge holds while one is open, an outcome that writes no record because R7 routes the step. Known progress only: a legacy plan (`steps: unknown`) is unaffected. Scaffolding steps count, named with their `step-close`.

#### 4.2.4 Already present (R10) *(my call; required once R9 lands)*

A `verify-red` that finds a step's behavior already on the base closes the step "already present", journaled with that run. `evidenceForDiff`'s latest-red scan skips an already-present red, and a tag left with no genuine red passes the evidence check. Without this, a step whose behavior predates it never closes (P9), and R9 removes today's only way past one: a hand-run gate whose evidence fails, then an upstream revise.

#### 4.2.5 Un-parking (R11) *(the user's decision Q3; the readers are my call, from passes 2–4)*

- `witness decide <gate> <target> --revise --note "<why>"` is legal on a parked run below the bound, by a human only: it refuses inside a drive session (the pattern of rows 205, 207 and 225) and for policy and arbiter acts. It lifts the park without running the gate, and `next` then routes the owed work, steps first.
- D94's revised anchor reads only the decisions after the last un-park, so approve and stop stay reachable.
- The parked row offers the revise alone while work is owed — an open step, a plan reopen, an evidence row — or when the parked gate's latest act sent work upstream; otherwise both, each on a labelled row of its own (`revise:`, `fresh:`), never one `exits:` line. `status` prints each reopen act raw on a row of its own under its table, never inside a TOON cell; `decide --show` gains a `parked` state; the parked head names who parked it (`parked by the arbiter — <reason>`); and a `--fresh` refused on a parked gate is a human call naming the revise on a row of its own.
- A human un-park restarts drive's cap window, as a cap park does (`caps.ts:31-34`). An upstream reopen still un-parks (row 124). At the bound the endgame set stays.

#### 4.2.6 Re-runs (R12) *(my call, from pass 2)*

While a step is open, a settle's routed re-run is the flow's step row — stage implement, home the worktree, its model; the routed result carries the whole row — never `gate implement`.

### 4.3 Row 242 — a hold only the human can clear is a human stop (#90)

#### 4.3.1 Outcome classes (R13) *(the user's decision Q4; the classes are my call)*

| Class | Ship outcome | What follows |
| --- | --- | --- |
| **merge** | The approved commit is on the PR and only CI is missing: no CI checks, or none that passed. In both modes — autonomy off also waits `ship.ciSettleMs` before believing "no checks" — and for every merge left to a human today: autonomy off, autonomy turned off during the watch (`ship.ts:211-214`), a base whose own config says autonomy is off (`:251-253`). | A human stop. |
| **fix** | What an approval cannot merge: a PR branch holding commits the worktree lacks; a push the remote's lease rejected; GitHub's merge refusal; a PR base other than `ship.branch`; *(my call)* a CI with a failed or cancelled check. | A human stop, never a merge command. |
| **transient** | The remote did not answer, or CI has not finished: a failed fetch; an unreadable PR base; any other push failure; checks still pending when the watch closed (no longer `ci: red`); *(my call)* a check set that could not be read. | Drive re-checks by itself (§4.3.4). |
| **re-gate** | The approval lapsed or the base moved (`ship.ts:257-265`); a merge refusal after the base moved since the check. | Machine work: `witness ship` rebases and re-gates. |
| **re-route** | A step is open (R9). | `next` routes the step; no record. |

- **Rows.** A merge stop prints `waiting: merge · <plan> · PR #N — <reason>`, then `  run: gh pr merge N --<ship.merge> --match-head-commit <pushed sha>` — through the offered-line renderer, the number and the sha checked; this also fixes today's bare `gh pr merge N` row (`src/needs-you.ts:199-201`) — then `  recheck: witness ship <plan>`. A fix stop prints `waiting: fix · <plan> · PR #N — <reason>`, the remedy in plain words, `  run: gh pr edit N --base <ship.branch>` for the base case alone, then `  recheck: witness ship <plan>`. GitHub's refusal text prints through `logSafe`.
- **Classification comes from the record** (§4.3.2): drive's `classifyAction`, `next`'s `humanStop`, `driveHasWork` and `humanAction` read it, never the text. `MERGE_LINE` (`drive.ts:467`) and the `merge PR` text test (`drive.ts:89-91`) retire. `wait`'s merged-on-GitHub poll covers merge and fix stops.
- **A red CI stays the human's** *(my call; n5)*: the fix row reads `CI failed — <bucket: name · …>` and says to fix the cause — a flaky check re-run on GitHub, or a code change in the worktree, which moves the tree, so `recheck` re-gates (row 174's lapse). A failed or cancelled check counts as red only on positive evidence from the check set (`gh pr checks --json name,bucket`); a non-zero `gh pr checks --watch` whose set cannot then be read is transient.
- **Git's words.** A rejected push is read from git run with `LC_ALL=C` and `--porcelain`, so a localized git still classifies (W7).

#### 4.3.2 The record (R14) *(the user's decision Q5; the entry is my call)*

- `witness ship` journals every watch outcome as one entry kind, `ship-watch` `{pr, head, base, outcome, reason}` — `head` the commit pushed before the watch, `base` the remote ship branch's commit as ship last fetched it, `outcome` one of `merge`, `fix`, `transient`, `pending` and `re-gate` — unless the plan stream's latest entry is a `ship-watch` with the same fields. `ENTRY_PROGRESS` classes it `act` (`src/progress.ts:10`, whose build fails without a row). *(`re-gate` is my call, from this write-up: with no record, drive never runs the re-gate session — P15.)*
- A `merge` or `fix` record **stands** while it is the plan stream's latest entry, the worktree's HEAD is its `head`, and the base has not moved as far as this machine last fetched: the local `refs/remotes/origin/<ship.branch>` still equals `base`, or moved past it by state commits only (row 96's rule). *(My call: `mergeOwnPr`'s base check without its fetch, because `next` never fetches; pass 4 asked for the row to lapse on a moved base.)*
- While one stands, `next` never routes `witness ship` for that plan — and this applies only where `flowStep` would have routed ship, below R7's rows. The plan is skipped as a parked gate is, and its `waiting:` rows print above the routing block from `needsYou`, which derives `merge` and `fix` items from the journal, so they survive a drive restart. Any later entry, a moved HEAD or a moved base ends the record, after which `next` routes `witness ship` again (a moved base re-gates); `witness retry` ends one the same way, by being a later entry.
- **Drive** sets a plan with a standing record aside as `merge` or `fix` in a pass beside the settle pass each round, from the journal, so a run left with only such stops pauses for the human (row 202). Row 207's take-back releases it when the record stops standing or the plan ends.

#### 4.3.3 A session's ship (R15) *(my call, from pass 2)*

Inside a drive session, `witness ship` on a standing `merge` or `fix` record for the same head returns at once with the stop's rows; a human's `witness ship` re-checks, and its outcome replaces the record. Drive's spawn-timeout and no-progress paths report a standing record as its stop, never as stuck.

#### 4.3.4 Drive re-checks a transient hold *(the user's pass-4 decision; the mechanism is my call, from this write-up)*

- When a lane ends and the plan's latest entry is a `transient` or `pending` record for the worktree's HEAD, drive sets the target aside as `recheck` with a due time: 5 minutes after the first, doubling to at most 60 minutes (constants; n3). Its progress is cleared, as after a usage limit, so the unchanged line never reads as stuck; its sessions and their time count toward `drive.caps` (row 183).
- A `recheck` aside is drive's own timer, never the human's: it is never published, listed by `needsYou`, notified or counted toward a pause for the human (today every aside would trip that pause, `drive.ts:1097`). When its time comes it is released at the top of the round and competes for a slot, and a new ship session re-checks. With no lane running, drive sleeps until the earliest due time; paused for the human, it also wakes then.
- At a cap — most likely `drive.caps.spawns` — the cap's own path takes over: the ship gate is settled, so nothing parks, and the target is set aside `capped` with the cap's note, a stuck row with `witness retry` — the first wake this hold produces.
- With no drive, `next` routes `witness ship` for a `transient` or `pending` record, which re-checks. Autonomy off, a human's `witness ship` journals the same records, so the rows read the same in every mode, and a `--manual` drive sets the same asides.

### 4.4 Docs, prompts and skills

- **`plugin/commands/witness.md`:** a `busy:` row — another witness run is acting on that target now; do nothing for it, no retry and no other verb on it; in a session drive started, end the turn; in a chat, say so once and keep matching. `waiting:` handling — `merge`: the human merges (they paste the `run:` line or merge on GitHub); never run it yourself, even when asked; run `recheck:` only when they ask. `fix`: tell them the reason; run `recheck:` only when they say it is fixed. `parked`: `revise:` sends the work back — run it only when they ask, with their reason as the note; `fresh:` re-runs the review on the work as it stands; if unclear, ask which. `stuck` and `capped`: `witness retry` only after a fix witness cannot see. A `wait: older drive` row: tell the human, with its `run:` line; end the turn; never run that line, and never wait again until they say go. `witness check` with `note: nothing is owed` in a chat ends the turn.
- **witness-ship:** never run `witness decide`; never merge or run a `gh pr merge` line. `merge: held — the ship approval lapsed` → run `witness ship` again. The steps-open hold → hand back to /witness. A merge or fix stop → render it and end the turn; running ship again returns the same stop. A transient hold → end the turn; drive checks again. `busy:` → end the turn.
- **witness-implement:** `step-required` applies before the first implement gate and after it while any criteria step is open; steps an amendment added are worked like a fresh plan's, from `steps:`; a `gate implement` refused `steps-open` names the next step; a `verify-red` that closes a step as already present prints the slice lines too; a fix round runs only once no step is open, so its cycles name no `--step`.
- **witness-plan:** changed work gets a new step id; a closed id stays closed.
- **`README.md`:** `--step` after a gate, the un-park, the merge and fix stops, and the upgrade note.

## 7. Edge cases and residuals

- **A lock miss** — a holder frozen past its `until` (a sleeping host), a reused Windows pid — lets a second settler pay one more model call, or a second ship run start; the token keeps the record, and a merge is pinned to its head. A reused pid frees at `until`. (This replaces v4's "two terminals with no drive": every settler takes the lock before it reads, so two terminals no longer both pay.)
- **Two ship runs that both reach the merge** after a miss: GitHub merges once, and the second records a fix stop from its refusal until the lazy stamp marks the plan done on the next `next`.
- **A step rewritten under its old id** stays closed; the plan stage gives changed work a new id (skill text).
- **Every evidence cycle wipes `.witness/screens/<plan>`,** so a UI gate can refuse screens after a red; the refusal names the green re-run.
- **A no-CI record goes stale if CI is added later;** `recheck` re-checks.
- **A base moved on the remote that nothing on this machine has fetched** leaves a merge row offered; GitHub merges the pinned head onto the moved base unless branch protection requires an up-to-date branch. `recheck` fetches and re-gates.
- **A human's `witness decide` while a settler's arbiter thinks:** the human wins, and the settler's act refuses `settled-since`.
- **Parks the old race wrote** stay in the journal; the un-park lifts them.
- **`wait`'s two-token rule** misses one rare shape: one stop turning busy while another arrives busy between two waits wakes the chat once.
- **A busy target that never frees** (a reused pid up to its `until`) keeps drive polling rather than ending.
- **Windows checks** (the human's, c3): W1 lock take and release under Defender and the indexer, with three concurrent takers · W2 `taskkill /T /F` mid-settle and mid-watch: a dead pid's lock freed at once, a reused pid's at `until` · W3 the busy folder and the steal guard under a synced or scanned `.witness/` · W4 the Pi add-on's `wait` (row 204): a busy stop stays silent, a stop left for a human wakes once, a merge record wakes · W5 a no-CI repo under `drive --detach` (row 223): one ship session, the merge set aside, `gh pr merge … --match-head-commit` pasted into PowerShell · W6 an old paused drive across the upgrade · W7 a rejected push read under a localized git.
