## 2. Goals, non-goals, anti-goals

**Goals**
- g1. One stop, one decision: no settler's act lands on a disposition it did not read, and a settle that loses is a no-op, never a park (#88).
- g2. One model call per stop, and one ship run per plan, wherever drive, a chat and a terminal meet; a miss costs a call or a run, never a wrong record.
- g3. The chat is woken only for what needs the human, and once.
- g4. A plan's unbuilt steps are its next work before and after an implement gate, and no gate runs while one is open (#89).
- g5. Every parked gate offers a way back that can succeed (#89).
- g6. A hold only the human can clear is a human stop: reported once, no more sessions, not stuck, no `witness retry`, a wake that names it — and it survives a drive restart (#90).
- g7. A hold that clears by itself is re-checked by drive, within its caps.

**Non-goals**
- n1. Who settles is unchanged — the policy, the arbiter, the kept stops (row 173); only what happens when two try at once changes.
- n2. No full lease: no renewal thread, nonce fence, cross-target claim or session handle (the user's pass-4 answer).
- n3. No new committed setting and no `witness migrate`: every new bound is a constant or derived from an existing setting (row 202's precedent).
- n4. A holder that outlives its lock's bound — a sleeping host, a drive session stretched past its deadline by a sleep, or outside a session a wait longer than the estimate — may let a second settler pay one more model call, or a second ship run start; the record stays right. A reused Windows pid only delays the next taker until the bound.
- n5. Witness never withdraws a ship approval because CI failed: a red CI stays the ship session's to fix, as the ship skill already says (`plugin/skills/witness-ship/SKILL.md:47`).

**Anti-goals**
- A park, or any settler's act, appended on top of a decision it never read.
- Telling the human to retry what cannot change, or offering a merge for a PR whose branch or target is not what was approved, or whose base moved since.
- Waking the chat for a stop drive is deciding.
- A plan step left unbuilt behind a passing implement gate that no human approved past it.
- Overwriting a commit someone else pushed to a PR branch.

**Constraints**
- c1. Witness only; upgrading a consumer is the user's call, made separately.
- c2. An upgrade must not leave a tree dirty, and must not re-queue a plan — except to re-witness, once, a step an amendment added after an implement gate and 0.28 let be built without a step tag (§4.2.1). New files live under `.witness/live/`, which state commits already exempt (`src/gitio.ts:126`) and the live writer excludes first (`src/live.ts:50`).
- c3. Windows behavior is measured by the human before a row says MEASURED (W1–W7, §7).
- c4. 0.29.0: a new journal entry kind and a newly legal decision. Once a 0.29.0 CLI journals anything, the state floor — the highest `w` stamp in the journal (`src/floor.ts`, row 116) — refuses every older CLI at dispatch. An older drive already running is not refused, because the floor is read only at dispatch (`src/cli.ts:187-199`; P13).

## 4. The design

### 4.1 Row 240 — one decider per stop (#88)

A token checked under the state lock keeps the journal right (§4.1.1). Busy locks (§4.1.2) only spare model calls, duplicate ship runs and false wakes, so a lock that misses costs a call or a run, never a wrong record. *(The split is the user's pass-4 decision; the mechanism is my call.)*

#### 4.1.1 The settled-since token (R2) *(my call, from passes 2–6)*

- Every settler's act — the policy's, the arbiter's, `parkRefused`, the park after two malformed answers, a cap park — carries a token: a hash of every `human-decision` line of that gate after the run it judged (that gate's `caused_by` reopens included), taken from the settler's own read before any model call: `settleStop`'s read, or `parkAtCap`'s.
- `applyDecision` compares the token first, before the repair, bound and anchor checks, and again under the state lock beside the `nothing-pending` and `anchor-moved` re-read (`decide.ts:614-625`). A mismatch refuses `settled-since`.
- `parkRefused` runs only for an arbiter choice refused on a run still owed in the same form — the same `run_id` and the same token — and carries the original token.
- Human acts carry no token. A human's `decide` while a settler's arbiter thinks wins, and the settler's act refuses `settled-since`.
- Applied with no lock at all, the token refuses the loser in all eight replayed shapes — the seven races of P3 and a cap park read before a human's repair — the journal keeps the winner, and the 102 tests of seven decision test files pass unchanged (P4).

**What `settleStop` returns**, and what its readers do *(passes 5 and 6)*:

| Kind | When | Readers |
| --- | --- | --- |
| `superseded` | The door refused `settled-since`, or a re-read after any refusal shows a decision landed on the judged run. | Printed `decided: <gate> <target> → <decision> · <by> (decided first)`. Every reader treats it as `decided` with the winner's decision: `settledCode`, ship's carry-on after an approve (`ship.ts:448`), the gate's hand-over, `next`'s canon reload (`next.ts:1256`). A winning revise prints the revise-context rebuilt from the journal, as `decide` prints it, since the stage skills fix "from the revise-context it printed". |
| judged again | A stale-verdict or hold-lifted refusal: the content moved while the arbiter judged. | One more evaluation from a fresh read, as the stale stop it now is: below the bound the policy routes the re-run (`routed`, no model call); at the bound `bound-recurrence` takes `revise-upstream` (no call) and `bound-stale` asks the arbiter about the content as it is now (one more call, the content the first ruling judged being gone; P26). Never a park on the old ruling. |
| `moved` | A newer run is owed (`anchor-moved`). | Nothing for the human: that run's own settle decides it. Ship's awaiting-decision path ends without rendering a decision block (today it would render `none` as a `--manual` stop, `ship.ts:451-467`). |
| `busy` | Another live process holds the stop's settle lock (§4.1.2). | Where a verb settles (the gate tail, ship's awaiting-decision settle): `busy: <target> — another witness run is deciding <gate> (pid N, since HH:MM)` and exit 3. In `next`'s and drive's passes nothing prints; the route's `note: being decided` covers it. |

#### 4.1.2 Lean busy locks (R1) *(the user's decision; the shape is my call)*

- **Where.** `.witness/live/busy/<target>.settle.json` and `.witness/live/busy/<plan>.ship.json` — machine-local, under the folder state commits exempt (c2), refused through a symlinked folder as `live.ts` refuses one. A target names a file only after it passes the id rule.
- **Shape.** Created exclusively and without following a link (`O_CREAT | O_EXCL | O_NOFOLLOW`), holding `{pid, since, until}`. An empty or unreadable file is a write in progress for one second, as the repo lock reads one (`src/lock.ts:12-14`).
- **The bound.** `until` is written by the taker, so no reader computes one from its own config: `until = min(max(estimate, the session's deadline), since + 24 h)` *(pass 6: the cap goes last, P20)*. The session's deadline (`WITNESS_DRIVE_DEADLINE`, inside a drive session only) is the earliest time drive may stop the session — a host sleep moves its stop later — and a reviewer inside it may wait out a usage limit until then (`src/reviewer.ts:262-285`). A lock whose `until` lies more than 24 hours after its `since` reads as stale. The estimate covers what can be bounded; a test suite, git or a runner turn has no timeout outside a session (n4, §7).
  - Settle lock estimate: `2 × 3 × gates.reviewerTimeoutMs + 2 × LOCK_WAIT_MS + 2 min` — a self-repair reroll is a second arbitration, each of up to three timed attempts (`reviewer.ts:146`), then the door's lock wait, twice when `parkRefused` follows.
  - Ship marker estimate: `3 × gates.reviewerTimeoutMs + ship.ciSettleMs + 30 min + 2 × the settle estimate + 10 min` — the gate's battery, the CI watch, both settles, git and gh.
- **Live** means the pid is alive and `until` has not passed. A lock that is not live is taken over through `takeStale`'s steal guard, as the repo and drive locks are (`lock.ts:76-95`). A lock naming the reader's own pid is not busy to it — no lock nests: the settle lock and the ship marker are separate files, and each is taken once per act — and drive removes its own leftovers each round. `EPERM`, `EBUSY` or `EACCES` on create is retried a few times within a second; a create that still fails refuses `lock-unwritable` naming the folder, as the repo lock does (`lock.ts:133-137`), never "busy" forever. An unlink that keeps failing leaves the lock to the dead-pid rule. Nobody ever waits for a lock.
- **The settle lock** is taken by `settleStop` before it reads the stop — the gate tail's settle, ship's awaiting-decision settle, `next`'s pass and drive's pass all go through it — and by `parkAtCap` before it reads the stream; it is held through the arbiter call and `applyDecision`, and released in `finally`. Held by another live process: `settleStop` returns `busy` and reads nothing; `parkAtCap` reports busy and parks nothing, and drive's `capped()` then sets nothing aside: the target is tried again next round (today a refused park is set aside `capped`, `drive.ts:926-935`).
- **The ship marker** is taken by `witness ship` at its start, before it journals anything, and released in `finally`. Held by another live process: `witness ship` refuses exit 3 before journaling, `busy: <plan> — witness ship is running on it (pid N, since HH:MM) · nothing to do; it continues when that ends`.
- **Drive.**
  - `admits()` skips a target whose settle lock or ship marker another live process holds, and one whose settle awaits its retry (§4.1.4), so the settle pass, the fill, `waitingNeed`, `capped` and `unmoved` never meet it.
  - The settle pass admits a target in drive's scope (the `--flow` claim, else every target) that is not itself a lane, not set aside (`retry` and `recheck` included), and not busy to another live process — a lane's family members included, which today's `admits()` keeps out; the fill still holds a lane's whole flow *(my call, pass 5: a spec's stop otherwise waited for every lane of its plans to end, P18; the predicate spelled out in pass 6)*.
  - While an admissible target is busy and no lane runs, drive polls on its pause cadence — no pause for the human, no notification — instead of ending its run; the busy folder joins `watchSignature`, and a lock is never renewed, so only a take or a release changes it. Drive's own timers (`retry`, `recheck`) wake it at their due times, since the repo lock is outside `watchSignature` (P25).
  - Drive drops the locks of dead pids when it starts and after every session, `releaseDeadTurn`'s pattern (row 218), before Windows can hand the pid to another process.
  - A lane whose target is busy when it ends — a human started `witness ship` after drive spawned — ends like a usage-limited lane: progress cleared, no cap counted, never stuck. Drive reads the busy folder for it, not the session's words.
- **An older drive.** `drive.lock` gains `busy: 1`, on row 224's `lease: 1` precedent. A 0.29.0 `next` or `wait` that sees a live drive lock without it settles nothing and prints `wait: older drive — a witness drive from before 0.29 runs this repo · stop it, then say go` with that drive's stop command on a `run:` row (the `watch:` line's stop, rows 180 and 201). A 0.29.0 drive reads the state floor each round and, once a newer CLI has written, ends with `EndReason` `superseded`, "a newer witness CLI took over". The release notes say to stop drive before upgrading.
- **What a miss costs.** A holder that outlives its bound lets a second settler or ship run in: one more model call, or one duplicate ship run, never a wrong record (the token, and a merge pinned to its head). A dead pid frees at once; a reused one delays the next taker until `until`.

#### 4.1.3 Cap parks (R3) *(my call, from pass 3)*

A cap park lands where it does today, on the latest open gate (`caps.ts:71-72`), now under the settle lock and with a token from `parkAtCap`'s own read. One after a `revise` or `revise-upstream` is drive's deliberate flow park (row 183), and its parked row offers the revise alone (§4.2.5), which lifts it with the upstream reopen intact (P5). Retargeting the park onto the reopened gate was probed and dropped: the park discharged the reopen, and the revise then lost it. The invariant is "no settler's act lands on a disposition it did not read". So #88's third Expected — one run never carries both a revise and a park — holds for every settler's act except this deliberate cap park, and a human's D94 stop after a revise stays legal too (fewhats has five such runs, all done or abandoned).

#### 4.1.4 Retries (R4) *(my call; reworked in passes 5 and 6)*

- A settle the door refused with exit 3 — the repo lock held past its 30-second wait, a transaction that appeared meanwhile, an unwritable `.witness` — waits for a retry as a `retry` aside: drive's own timer, never published, listed, notified or paused for, due one lock wait (30 s) later. While it waits `admits()` skips the target, so the fill — which sets any `witness decide` line still reaching it aside for the human (`drive.ts:776-783`) — never meets it early (P25).
- When the refused act's making cost a model call — the arbiter's ruling, `parkRefused`'s park, the park after two malformed answers — drive keeps that act. When the retry falls due, the settle pass applies it again through `settleStop`'s own refusal handling (§4.1.1's table), without a model call, while the stop's run and token still match; a mismatch drops it, and the stop is judged afresh (P17).
- A busy lock never counts: it never reaches the door. Three door refusals with exit 3 in a row on one stop set it aside for the human, as every `left` is today (`drive.ts:896-898`; a usage-limited one becomes a pause, `:883-886`, and still does). A chat's `next` makes one pass and does not retry; a kept act dies with drive's process, and a restarted drive judges the stop afresh.

#### 4.1.5 What wakes and routes the human (R5) *(the user's decision "the chat leaves drive's stops to drive"; the readers are my call, simplified in pass 5)*

- **Drive's scope.** The live file (`.witness/live/drive.json`) gains drive's scope — the claimed flow under `--flow`, else every target — and `deciding`, which drive publishes as false once it has stopped settling for good (a ceiling, a usage stop, a spawn failure: while its lanes drain, nobody decides; pass 6). A stop **drive will decide** is one in its scope that drive has not set aside, while `deciding` holds: a lane's stops by its session, every other by the settle pass (§4.1.2). Every lane is in the scope, so v4's "lanes" add nothing.
- **The chat's `next` under a live 0.29.0 drive** settles only stops drive will not decide: outside its scope, or set aside by it (a stop left for a human after an arbiter failure stays the chat's to retry, as today). Its printed route skips a stop drive will decide, or one under another process's live settle lock, naming it once — `note: being decided — <gate> <target>` — and `next: witness decide …` prints only for a stop that needs the human. With no live drive the chat settles repo-wide, as today.
- **`needsYou`** — and through it `wait`, the report and drive's notifier — lists an owed decision in drive's scope only once drive set it aside as left for a human, never for a settle awaiting its retry or a usage-limit pause, and a pending transaction under a live drive only once drive set the recovery aside. Drive applies the same rule to itself.
- **`wait` is unchanged.** v4 also hid a stop under a live settle lock from `wait` and accepted two tokens; pass 5 showed that rule could miss a wake. A stop being settled outside drive's scope — by a terminal's gate, or a second chat — can wake a waiting chat once, whose `next` then says `being decided` (§7).
- These filters touch only what the human is shown — `humanAction`, `needsYou`, the printed route — never the ladder drive keys progress on.

#### 4.1.6 Old journals

Parks the old race wrote stay in old journals; the un-park (§4.2.5) lifts them. *(v4's R6 — refusing a gate run when a reopen of its gate landed during its battery — is out: the retry it caused re-ran the same battery, which never sees a reopen's note, and the re-run discharged the reopen just the same (P19). The defect predates this effort and moves to Open / deferred with a park landing the same way; my call.)*

### 4.2 Row 241 — unbuilt steps come first (#89)

#### 4.2.1 Routing (R7) *(the user's decisions 2, 8 and 9; the placement is my call, from pass 2; the two refinements are my calls, from pass 6)*

- An open plan reopen and an open step route above `flowStep`'s `pr` row (`next.ts:441`), and an open step is the next work before or after an implement gate: the `stepped` term drops `!implementGated` (`next.ts:475`). This extends row 95's reopen row to plans with a PR and reverses row 191's Plan's call 5.
- **A human's approve stays final (row 93; the user's decision 8).** A plan whose implement gate a human approved — with or without `--override` — while the plan's content is still what that approve judged, is past its steps: R7's step row and R9's ship check and merge hold do not apply to it. "What that approve judged" is the plan-content sha of the approved run, never the base or the tree: ship's own rebase moves the base, and must not end the pass (P28). A policy or arbiter approve gets no such pass. With decision 6 in force no new implement run can start with a step open, and an amendment changes the plan's content, so in practice the pass reaches approvals given before the upgrade (P29).
- **Steps built after a gate under 0.28.** 0.28 never required `--step` after an implement gate, so a step an amendment added after one, and that was built then, carries no tagged cycle and reads open under 0.29. R7 routes it again, and its re-witness is cheap and needs no code change: its red passes (vacuous), `verify-red` sets the plan's change aside and observes the genuine red on the base, and its green closes the step. This re-queues such a plan once (c2's exception). *(Pass 5's alternative — reading old untagged evidence after a gate as legacy — is out: every 0.28 fix round is such evidence, so it would have frozen the step tracking of every in-flight plan that ever had an implement revise, and later amendments would have reproduced #89 there (P31); my call.)*

#### 4.2.2 `--step` (R8) *(the user's decision; the wording corrected in pass 2)*

`test-evidence` and `verify-red` require `--step` before the first implement gate, as today, and after it while any criteria step is open (`src/steps.ts:180-183`). A fix round, with every step closed, names none.

#### 4.2.3 The steps-open refusal (R9) *(the user's decisions 6 and 9; ship's part is my call, from pass 2)*

`gate implement` and `witness ship` — whoever runs them — refuse `steps-open` while a step is open, before the battery, journaling nothing, naming the step's command; `decide`'s refusals name it too. The ship gate's `implement-gate` check (`src/gates/ship.ts:77`) fails while a step is open, and ship's merge holds while one is open, an outcome that writes no record because R7 routes the step. Known progress only: a legacy plan (`steps: unknown`) is unaffected, and so is a plan a human approved past its steps (§4.2.1). Scaffolding steps count, named with their `step-close`.

#### 4.2.4 Already present (R10) *(my call; required once R9 lands; made precise in passes 5 and 6)*

- A `verify-red` that finds a step's behavior already on the base — the test passes with the plan's change set aside — closes the step "already present" by journaling a `step-close` entry marked `present`, an act, and only while the step is still open: it moves drive's progress and counts as the session's act (`src/progress.ts:26`, `src/slice.ts:32-35`), where today's vacuous red counts as neither.

#### 4.3.1 Outcome classes (R13) *(the user's decision Q4; the classes are my call, revised in passes 5 and 6)*

#### 4.3.2 The record (R14) *(the user's decision Q5; the entry is my call, revised in passes 5 and 6)*

- **The entry.** `witness ship` journals the outcome it ends on, whichever phase, as one entry kind, `ship-outcome` `{pr?, head, base?, outcome, reason, n?}`: `pr` absent before a PR exists; `head` the worktree's HEAD at the outcome; `base` the remote ship branch's commit as ship last fetched it; `outcome` one of `merge`, `fix`, `transient`, `pending`, `red`, `re-gate` and `merged`; `n` the attempt count of a `transient` or `pending` run of outcomes. A `transient` or `pending` record is always journaled, so drive can tell a re-check from a session that did nothing (§4.3.4); any other one is skipped when the plan stream's latest entry is a `ship-outcome` whose `{outcome, pr, head, base, reason}` are the same — a red's reason built from the failing checks' names, never the whole line, which carries `w` and `ctx` (`src/journal.ts:106-110`). `ENTRY_PROGRESS` classes it `act` (`src/progress.ts:10`, whose build fails without a row). *(`re-gate` is my call, from the write-up: with no record, drive never runs the re-gate session — P15. `merged` is from pass 5: without it, a record outlives its PR — P22.)*
- **One predicate, every reader** *(pass 6)*. A plan is **held** when a `merge` or `fix` record stands — it is the plan stream's latest entry and the worktree's HEAD is its `head` — and `flowStep`'s rows above its ship row route nothing: no open plan reopen, no open step (R7). `flowStep` answers a held plan with its stop rather than `witness ship`; `needsYou` derives its `waiting:` rows from the same predicate, so they survive a drive restart; drive's held pass uses it too. So the global ladder, `next --flow`, a worktree's ambient `next`, the report and drive agree, and an amendment that opens a step is routed to that step, never offered as a merge (P21).
- **GitHub moves on** *(passes 5 and 6)*. While a `merge` record stands, `next` checks it where its lazy stamp already reads the PR (`src/stamp.ts:49-59`). The same `gh pr view` also reads `baseRefName`, and one `git fetch` of `ship.branch` per `next`, with a short timeout (git has none today, P32), feeds `mergeOwnPr`'s own `baseMoved` reading (`ship.ts:145-150`). From what it finds, `next` journals the record that follows:
  - a PR retargeted away from `ship.branch` → `fix`;
  - a PR closed without merging → `fix` ("reopen it, or abandon the plan");
  - a base moved beyond witness's state commits → `re-gate`;
  - a merged PR → the stamp, as today.
  A failure or a timeout reads as offline: nothing is journaled, and the row stands. A `fix` record is not checked for a moved base: a rebase cannot clear a human's hold, and a re-gate there would run a battery, and before the lease fix a forced push, for nothing (P27).
- **`wait`** reads the same PR fields on its two-minute poll and wakes the chat only when they differ from what the standing record says — a merge stop's PR merged, closed or retargeted — never again for the state the record already names; the chat's `next` journals it (`wait` journals nothing).
- Any later entry or a moved HEAD ends a record, after which `flowStep` routes `witness ship` again; `witness retry` ends one the same way, by being a later entry.
- **Drive** sets a held plan aside as `merge` or `fix` in a pass beside the settle pass each round, so a run left with only such stops pauses for the human (row 202); row 207's take-back releases it when the plan stops being held or ends. A `merged` record ends the plan for drive at once, as a done plan does: no further session runs only to reach the stamp.

#### 4.3.3 A session's ship (R15) *(my call, from pass 2)*

Inside a drive session, `witness ship` on a held plan's standing record returns at once with the stop's rows; a human's `witness ship` re-checks, and its outcome replaces the record. Drive's spawn-timeout and no-progress paths report a standing record as its stop, never as stuck.

#### 4.3.4 Drive re-checks a transient hold *(the user's pass-4 decision; the mechanism is my call, from the write-up, revised in pass 5)*

- A lane that ends after writing a `transient` or `pending` record — its progress key moved during the lane, and that record is now the stream's latest entry — sets the target aside as `recheck`, due 5 minutes after the first, doubling to at most 60 (constants; n3). A lane that wrote nothing takes today's no-progress path and ends stuck: a session that never reached ship is not a re-check.
- Its progress is cleared, as after a usage limit, so the unchanged line never reads as stuck. When its time comes the aside alone is deleted — the target's per-run use, its progress, drive's idle clock and its notified keys stay as they are (row 207's release resets them and must not be used, or no cap would ever trip) — and the target competes for a slot; a new ship session re-checks.
- A `recheck` aside is drive's own timer, like `retry`: never published, listed by `needsYou`, notified or counted toward a pause for the human (today every aside would trip that pause, `drive.ts:1097`). With no lane running, drive sleeps until the earliest due time; paused for the human, it also wakes then. Re-checks are drive's own work, so the idle limit does not run meanwhile.
- Every re-check is a ship session counted toward `drive.caps` (row 183). At a cap — most likely `drive.caps.spawns` — the cap's own path takes over: the ship gate is settled, so nothing parks, and the target is set aside `capped` with the cap's note and the last record's reason, a stuck row with `witness retry` — the first wake this hold produces.
- **Modes.** The held pass, `retry`, `recheck` and the pause are autonomy's. A drive that is not autonomous (autonomy off, or `--manual`) never meets a held plan, which `flowStep` answers with its stop; the report shows it, and the run ends as today when nothing else moves. A lane that ends on a `transient` or `pending` record there is set aside as stuck: the human is at the terminal. With no drive at all, `next` routes `witness ship` for a `transient`, `pending` or `red` record, which runs again.

## 7. Edge cases and residuals

- **A holder that outlives its bound:**
  - inside a drive session the bound is the session's deadline, which a host sleep can stretch;
  - outside one, a test suite, git or a runner turn has no timeout, and a sleeping host stops the clock nowhere;
  - in either case a second settler pays one more call, or a second ship run starts; the token keeps the record, and a merge is pinned to its head.
  - A reused Windows pid delays the next taker until `until`.
- **Two ship runs that both reach the merge** after a miss: GitHub merges once, and the second journals a `fix` record from its refusal until the lazy stamp marks the plan done on the next `next`.
- **A stop being settled outside drive's scope** — a terminal's gate tail, a second chat — can wake a waiting chat once; its `next` says `being decided`.
- **A base moved on GitHub with no chat open** is noticed at the next `next`; until then a merge row stays offered.
- **A step rewritten under its old id** stays closed; the plan stage gives changed work a new id (skill text).
- **Every evidence cycle wipes `.witness/screens/<plan>`,** so a UI gate can refuse screens after a red; the refusal names the green re-run.
- **A no-CI record goes stale if CI is added later;** `recheck` re-checks.
- **A human's `witness decide` while a settler's arbiter thinks:** the human wins, and the settler's act refuses `settled-since`.
